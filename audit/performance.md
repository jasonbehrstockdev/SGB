# Performance improvements

For subsequent 1,000- and 3,000-vertex comparisons, see the
[20-graph density study](performance-ensemble.md) and the earlier
[single-graph report](performance-large.md). The original 100-vertex
measurements below remain preserved.

The comparison baseline is the repaired version at commit
[`cbdb90f`](https://github.com/jasonbehrstockdev/SGB/tree/cbdb90fb17186288f6a77944f2ee84dee2c4f230),
before this optimization pass. The original 2024 import and all previous audit
evidence remain preserved. The baseline source and executable were saved and
measured before editing the algorithm; the [initial pre-edit measurements](performance-initial-baseline.json)
are retained separately from the repeated paired measurements.

## Measured results

The optimized version is **2.91× faster by the equal-case geometric mean** on
the 21 selected 100-vertex graphs. Benefits depend strongly on structure:
graphs with many overlapping squares improve much more than graphs whose cost
is dominated by searching adjacency lists.

Each entry below is the median of seven timed runs per build. Both builds read
the same number of repeated records in each process. Times include process
startup, parsing, analysis, cleanup, and CSV output, divided by records per
process. They are batch-throughput measurements, not single-request latency.
The full [raw results](performance-results.json) retain every timing, ranges,
execution order, warmups, batch sizes, graph/source/binary hashes, and environment.

The sparse ER cases are essentially unchanged. The square-free cycle is about
8 microseconds slower per graph in this run; it is a measured regression, not a
speedup. Its very short batches are particularly sensitive to overhead and
machine noise. The K20 join case is also essentially unchanged, despite having
only 191 squares: adjacency searches, rather than square connectivity, dominate.

The corpus consists of the original 15 studied graphs plus six deliberately
chosen workloads. It is not a random sample of all 100-vertex graphs. The
[graph records](../benchmarks/performance-graphs.txt) and
[construction metadata](../benchmarks/performance-metadata.json) are committed.
The small-world fixture is generated by Python with a fixed seed; its saved
edges, rather than a promise of cross-language RNG identity, define the input.

Measurements used GCC 14.2.0, Boost 1.83, C++11, `-O2`, and
`-Wall -Wextra -Wpedantic -Werror` on Linux x86_64, with an AMD EPYC 7763 CPU
reported by the container. The container had a four-CPU quota and 16 GiB memory
limit. Builds/tests were paused during measurement. The host was not exclusively
reserved or CPU-pinned. Runs alternated before/after order, with one warmup per
build and calibrated common batch sizes. Calibration targeted 50 ms for the
faster build, capped by 256 records and a 500 ms slower-build budget; slow single
records can exceed that budget, and fast batches can fall short of the target.

These numbers describe ordinary `-tf` analysis. Full verbose/debug graph
construction and printing were checked for correctness but are not included in
the speedup claims. Peak memory was not measured. Compiler/source metadata and
exact build commands document the builds used; hashes identify the artifacts,
rather than proving build provenance on another machine.

These probes support targeting deduplication and connectivity, and show that
the K20 join workload is dominated by enumeration. Their absolute timings are
not additive decompositions of the main benchmark: they exclude parsing,
supports, classification, output, and destruction after the timer, and use a
different executable and allocation history. In particular, the K20 probe shows
slower enumeration after the change even though the actual CLI comparison is
essentially unchanged. Compilation/layout and process history are possible
contributors; this discrepancy was not isolated. Use the repeated actual-CLI
results above for speed claims, rather than deriving extra speedup claims from
these diagnostic probes.

## What changed

1. **Square deduplication uses a hash set.** Sort the endpoints of each diagonal,
   then order the two diagonals. This gives every orientation of the same square
   one key. Hash collisions are resolved by full-key equality. The result vector
   retains its original discovery order and diagonal orientation.
2. **Square components use a diagonal index.** Each square contributes two
   incidences. Squares sharing a diagonal form a clique; unioning them with one
   representative computes its connectivity without constructing its edges.
   Component labels are assigned by first square occurrence so presentation
   remains deterministic despite hash-table iteration order.
3. **The full square graph is constructed when requested.** Verbose and debug
   modes emit every pair within each diagonal bucket. Distinct squares cannot
   share both diagonals, so an edge is emitted exactly once. Ordinary CFS and
   statistics modes avoid allocating these edges. An omitted graph is represented
   explicitly, never presented as an empty graph or replaced by union-find edges.
4. **Support and output avoid unnecessary work.** Insert the four endpoints
   directly into the component's support, eliminating temporary sets. Graph
   serialization sorts existing neighbors instead of testing every possible edge.
   The printed vertex/edge ordering is unchanged.

These changes preserve the supplied graph's literal induced squares and actual
supports. Complete join factors remain permitted only in CFS classification;
their vertices do not acquire square support. There is no change to CSV schema,
flags, random generation, parsing, or the thickness conventions.

If there are `S` distinct squares and `R` candidate occurrences, deduplication
changes from a linear search per candidate (up to `O(R*S)`) to expected `O(R)`
hash operations. After enumeration, diagonal indexing and component discovery
take expected `O(S α(S))` time and `O(S)` additional space. Materializing the
literal graph takes expected `O(S + E_square)` time, where `E_square` is its
actual edge count. The old graph construction compared all `S(S-1)/2` pairs.
Hash-table bounds are expected bounds, not worst-case guarantees.

Enumeration still walks adjacency lists and performs edge queries. It can
dominate chord-rich or dense inputs. The program still stores every induced
square, and full graph output still requires space/time for all actual square
edges. These changes do not make arbitrary large inputs inexpensive.

## Correctness checks

The additional structural suite independently enumerates four-vertex subsets,
checks square adjacency pair by pair, and computes components by breadth-first
search. It compares full square sets, full literal edge sets, component
partitions, actual support sets, counts, ratios, CFS, and serialized edges in
both analysis modes. This is independent of the production neighbor-walk,
hash-deduplication, and union-find pipeline.

Its cases include the 15 existing 100-vertex graphs, reordered edges and
permuted vertices for each, targeted empty/chorded/overlapping/join cases, and
a 100-vertex graph with a complete bipartite core and pendant vertices.
Small cases target particular invariants; exhaustive six-vertex testing is
not used.

Full debug output was also compared byte for byte against the saved baseline
on all 15 existing benchmark graphs and all 13 original example records.
Both standard output and standard error matched exactly; see the
[comparison records](performance-equivalence.json).

The 20 application regression groups, 11 benchmark-checker tests, all 15 original
100-vertex reference cases, and all 57 structural cases passed in optimized and
AddressSanitizer/UndefinedBehaviorSanitizer builds. Leak detection was disabled
for sandbox compatibility. Every timed performance case also matched the
independent reference, and every timed CSV output matched the baseline exactly.
An independent review found no correctness defect in the core changes. A
reporting issue in the new timing runner was corrected and given a regression
test: an unsuccessful rerun
must mark its output incomplete rather than leave a previous completed result
looking current.

## Reproduce

From a checkout containing this change, with Boost in the normal include path:

```sh
mkdir -p build/performance/baseline-source
git archive cbdb90fb17186288f6a77944f2ee84dee2c4f230 main.cpp flags.h input.h | tar -x -C build/performance/baseline-source
g++ -O2 -std=c++11 -Wall -Wextra -Wpedantic -Werror build/performance/baseline-source/main.cpp -o build/performance/SGB-before
make CXX=g++ build/SGB build/sgb-reference
python3 benchmarks/performance.py --before build/performance/SGB-before --after build/SGB --reference build/sgb-reference --before-source build/performance/baseline-source --before-commit cbdb90fb17186288f6a77944f2ee84dee2c4f230 --boost-version 1.83 --output build/performance/results.json
make check
make sanitize
```

Use the installed Boost version in the metadata argument. For a nonstandard
Boost installation, give the same `-I` option to both compilations, use
`CPPFLAGS=-I/path/to/boost/include` with Make, and include that option in the
runner's `--compiler-flags` metadata. The recorded run used
`-I/tmp/sgb-boost/usr/include`. Rebuild both executables if compiler options
change; Make does not automatically invalidate a target when flags change.

`python3 benchmarks/performance_cases.py` regenerates the fixed performance
corpus. Keep correctness/sanitizer work separate from the timing run and avoid
concurrent builds or heavy workloads. Raw speed tests use optimized builds,
not sanitizer builds.

To reproduce the optional phase probe after building the baseline sources:

```sh
g++ -O2 -std=c++11 -Wall -Wextra -Wpedantic -Werror -DSGB_SOURCE='"../build/performance/baseline-source/main.cpp"' benchmarks/profile.cpp -o build/performance/profile-before
g++ -O2 -std=c++11 -Wall -Wextra -Wpedantic -Werror -DSGB_OPTIMIZED benchmarks/profile.cpp -o build/performance/profile-after
python3 benchmarks/profile.py --before build/performance/profile-before --after build/performance/profile-after --results build/performance/results.json --output build/performance/phases.json
```

Apply the same Boost include option to both probe compilations if needed.

## Remaining opportunities

Adjacency bitsets or common-neighbor enumeration are plausible next steps for
the enumeration bottleneck, but were not added without a separate measurement
and correctness pass. A reusable thickness API and general resource budgets
remain separate work. See the [original improvement plan](improvement-plan.md).
